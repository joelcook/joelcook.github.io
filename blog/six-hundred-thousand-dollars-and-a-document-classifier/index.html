Consultants wanted $600,000 to sort our files

Years of misfiled documents, a move from Workday to Banner, and a quote with a lot of zeros. We passed, and I built the classifier myself.

12 Sep, 2026

When the president of Indian River State College decided we were moving from Workday to Banner, it sounded like a fresh start. New system, clean slate! Except nothing about a migration is ever clean, because you have to drag the past along with you. And our past was years of documents, filed in broad categories that said nothing about where any of it belonged in Banner.

This is exactly the kind of problem that makes consultants’ eyes light up. It’s big, it’s scary, it smells like risk, and so naturally the price tag follows suit. One outside company put the classification work alone at $600,000. Six hundred thousand dollars! To sort files!

We passed. I built the classifier in-house instead, and that $600k is the spending we avoided. (That’s where the savings number comes from, before anyone asks.)

Here’s what the scary-problem pricing never accounts for: most of the evidence was already sitting right there in the export. Filenames, paths, existing categories. You don’t need a team of analysts to read a filename. You need rules a person can actually read, and an output the new system will actually accept.

So that’s what I built. Python rules around approved phrases and destinations. Normalized separators. And, crucially, known names and IDs masked before any matching happens, including names that turn up elsewhere in the input.

Why does that matter so much? Because my favorite bug in the whole project was two letters long. DE can mean Dual Enrollment. It can also be the “De” in somebody’s name. Let a matcher get a little too enthusiastic, and a student’s name becomes evidence about what kind of document they submitted. Tiny bug. Now repeat it across an entire migration! So the rule is simple: a filename has to say something about the document itself before it earns a placement.

When the evidence conflicted, the file went to an approved fallback. Yes, that makes the percentage look worse. I don’t care. It’s so tempting to juice the specific-classification number because it makes for a prettier dashboard, but the person digging through the wrong folder later isn’t going to be consoled by your dashboard.

The documented sample run covered 1,887 index rows. 1,396 got a specific document type, and 491 went to the approved Legacy Document destination. That’s a sample, not a claim that every document got inspected or that accuracy is 100%. But here’s the kicker: the run made zero LLM calls. Zero!

Now, there is a model-assisted path. It can use a local model through Ollama, or a cloud backend if someone explicitly flips it on. Either way, the model only ever sees redacted inputs, and its suggestions sit and wait for a human to approve them. But the rules don’t need any of that machinery to do their job. Which is exactly how it should be.

Then there was the file we actually had to hand over. Workday’s exports turned out to be .txt files with CSV inside and property values that looked almost, but not quite, like JSON. Lovely! And getting the categories right was worth precisely nothing if the corrected index choked the importer.

So the writer keeps the source formatting and swaps only the document-type value. The parser finds that property by its key, so it couldn’t care less if the columns move around. There are tests for line endings, quoting, reordered properties, and mismatched headers in the merged output. Every reviewer change gets a stable record hash and lands in an audit trail.

That’s the whole trick, really. Get close enough to an intimidating problem and it stops being intimidating. It turns into a list: a filing rule, somebody’s name, the exact shape of a text file. Not one item on that list needed a $600,000 proposal.

So the next time someone hands you a scary quote for a scary problem, open the export first. Read some filenames. You might just find you can build the thing yourself.
