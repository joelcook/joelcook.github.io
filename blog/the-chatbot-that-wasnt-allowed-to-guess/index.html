The Chatbot That Wasn’t Allowed to Guess

How I built and shipped a public AI agent for a college website — live on a site that sees ~250,000 visitors a month — by making “don’t make things up” a system constraint instead of a prompt.

23 Jun, 2026

River Guide is live right now on the website of Indian River State College, a site that sees around 250,000 unique visitors a month. It’s a public AI assistant — no login, anyone can use it — and it answers roughly 500 students a week. I designed, built, and shipped it solo.

Its most important feature isn’t a feature. It’s a rule: the assistant is not allowed to make things up.

That sounds like a prompt. It isn’t. It’s a system design constraint, and it ended up being the entire project.

so, I thought I was building a chatbot...

This seemed reasonable at the time. The River has a website. Students have questions. LLMs are good at text. So the obvious thing to build is a little chat bubble where a student can ask:

  • When is the drop deadline?
  • How much is tuition?
  • How do I register?
  • Why can’t I add this class?
  • Who should I contact?

That’s the intuitive product: a chatbot.

But after building and launching River Guide for the college students know as The River, I no longer think of the chatbot as the main thing. The chatbot is just the surface. It’s the UI over a more important object underneath.

The important object is the truth layer.

I ended up pulling that pattern into a separate open-source project called GroundTruth — a small, runnable blueprint for building AI assistants in a stricter way:

The assistant is useful, but it is not allowed to make things up.

Again: this is not a prompt. It’s an architecture.

The failure mode

The default way to build one of these things is roughly:

  1. scrape the website
  2. put the pages in a vector database
  3. connect an LLM
  4. ask questions
  5. hope retrieval found the right chunk

This is fine for a demo. It is not fine for a student asking about a deadline in front of a quarter of a million other people a month.

The problem is that organizations are full of facts that age badly:

  • dates
  • prices
  • office hours
  • phone numbers
  • term boundaries
  • course requirements
  • program requirements
  • portal instructions
  • names of systems currently mid-migration

The model can answer all of these. That is not reassuring. The model can answer them even when it shouldn’t.

This is the slightly cursed property of LLMs in production: the answer can be fluent, helpful, and wrong. More subtly, it can be correct today for the wrong reason — which means it becomes wrong later.

If River Guide answers the drop deadline from memory and happens to be right, that’s still a bug. It learned the wrong behavior. Next semester that same behavior fails, quietly, in public.

So the problem isn’t “get the answer right.”

The problem is “get the answer right by a path that will still be right after the facts change.”

The split

The key move was to split the knowledge base into two different things.

First, a database for hard facts.

Second, a wiki for explanations.

Hard facts are the things you can be harmed by getting wrong:

  • a deadline
  • a tuition amount
  • a fixed fee
  • a phone number
  • an email address
  • a course code
  • a prerequisite
  • a term start date

These go into SQLite. The assistant cannot answer them from memory. It has to call a tool.

Explanations go into a small, source-cited wiki:

  • how to apply
  • what financial aid verification means
  • what to do if a class is full
  • why a registration hold might appear
  • how the River Portal fits into the student workflow

The wiki is allowed to explain. The database is allowed to be exact.

This feels obvious after the fact. But most AI projects don’t make the distinction cleanly. They throw facts and explanations into one retrieval soup and ask the model to be wise.

GroundTruth does the opposite. It’s intentionally a little rigid. If a date or a dollar sign shows up in public wiki prose, a linter fails the build — not because dates and dollars are bad, but because they belong in the fact layer. The assistant can still say them. It just has to look them up first.

In practice, that one rule changes the whole shape of the system.

The runtime

At runtime, the model does not read files.

It talks to tools.

The tools expose two things:

  1. database lookups for volatile facts
  2. wiki search/read operations for explanatory content

So the behavior becomes:

  • “When is the drop deadline?” — the assistant calls get_deadline, then answers.
  • “How much is tuition?” — it calls get_tuition, then answers.
  • “Who do I contact?” — it calls get_contact, then answers.
  • “What do I do if I have a hold?” — it searches the wiki, reads the relevant page, then explains the workflow.

This makes the model more useful, not less. It can still summarize, translate, reason through the student journey, and turn institutional language into something a human can actually follow. It just no longer has permission to improvise the fragile parts.

The model is good at language.

The tools are good at facts.

The system should never confuse the two.

The shape of the thing

The architecture is small enough to hold in one mental model:

sources/
  captured data: scraped pages, exports, hand-authored YAML
        |
        | project
        v
db/groundtruth.db
  dates, dollars, hours, contacts, course facts

sources/
        |
        | compile
        v
wiki/
  source-cited explanations, no loose facts

wiki/ + db
        |
        v
MCP server
  read-only tools
        |
        v
LLM / chat platform

The important detail: the database is not hand-edited. It’s a projection from evidence. If a fact is wrong, you fix the source or the projection logic and rebuild — which gives you lineage.

The wiki is also compiled from sources, but it’s never the authority on volatile facts. It exists to make the institution legible.

When the wiki and the database disagree, the database wins and the page gets flagged.

That gives the assistant a simple worldview:

  • facts are looked up
  • explanations are retrieved
  • conflicts are surfaced
  • guesses are not acceptable

Evals are the product

The most important part of River Guide is probably not the prompt or the UI.

It’s the eval set.

I built a Golden 50: a fixed set of questions River Guide has to pass before it’s allowed to ship. These aren’t generic AI-benchmark questions. They’re the actual shapes of questions that matter for this domain:

  • deadline questions
  • tuition questions
  • financial aid questions
  • course and program questions
  • contact questions
  • personal-record questions the assistant must refuse
  • policy/process questions where it has to retrieve the right page

And here’s the part most people skip: the eval doesn’t only check whether the final answer sounds good. It checks whether the correct tool was used.

That’s the difference between testing prose and testing behavior. A model that produces the right tuition number without calling the tuition tool fails the eval. That answer isn’t trustworthy, because the behavior isn’t trustworthy — it just got lucky, and luck doesn’t survive a fact change.

This is maybe the most underappreciated part of shipping AI. Everyone wants the assistant to be accurate. Far fewer people build the mechanism that notices when it’s accurate for the wrong reason.

What it can’t do

The reason I trust River Guide in front of the public isn’t that it runs on a good model. It’s that the architecture removes whole categories of failure. Some things aren’t unlikely here — they’re structurally impossible:

  • It can’t state a deadline, price, fee, or contact it didn’t look up. There is no path from the model’s memory to a student. Volatile facts only reach an answer through a tool call against the database.
  • It can’t quietly go out of date. Every fact is a projection from a source. When the registrar moves a date, you fix the source and rebuild, and every answer that touches that date updates at once — with no prompt changes and nothing to re-teach the model.
  • It can’t invent when it’s stumped. If a fact isn’t in the database and the wiki doesn’t cover it, it says it doesn’t have that instead of filling the gap with a plausible-sounding guess. A “no” is more useful than a confident wrong answer.
  • It can’t answer questions about a specific student’s record. That’s a hard refusal, and it’s one of the cases the Golden 50 checks on every single build.

“Reliable” is a weak word for this. The point isn’t that it usually gets things right. It’s that the specific ways it could be wrong have been designed out of the system.

Shipping it to a quarter of a million people a month

Here’s where I think a lot of companies are misreading the AI opportunity. They’re hunting for magic in the model. But the model is one component. The value comes from the system you wrap around it — and most of that system is the unglamorous part.

Putting River Guide in front of the public meant it had to:

  • connect through Microsoft Copilot Studio with a custom connector
  • ship as a WordPress plugin that renders on the actual site
  • work on mobile, in a chat widget, without breaking
  • have file upload removed (a public, anonymous upload box is a liability, not a feature)
  • render tables without horizontal scroll
  • have a refresh button that actually restarts the conversation

And then there was the morning the bot was simply down: a stale Direct Line token had cached overnight and quietly broken everything. None of that is the exciting AI part. It’s also the job.

But scale and a public audience change the stakes in a way worth saying out loud, because this is exactly where the “don’t guess” rule earns its keep.

A public institutional channel cannot invent facts. When it’s just you and a demo, a hallucinated deadline is an embarrassing screenshot. When it’s a college’s official website answering hundreds of students a week, a hallucinated deadline is a real person who misses a drop date and eats a tuition bill. The refusal to guess isn’t a nicety here — it’s a safety property. The eval gate exists so that property is verified before the thing goes live, not discovered afterward in a support ticket.

The whole thing runs as an Azure Container App hosting the MCP server that exposes those read-only tools. Its auth model is deliberately minimal — a design decision, not a shortcut. Copilot Studio and the Azure-hosted MCP server authenticate to each other with a bearer token, service to service, and that is the only authentication the agent has.

There’s no user login, on purpose. Every fact the bot can reach is already public, so putting it behind a student account would be security theater — nothing it can say is anything a student couldn’t already read on the site. Once you’ve made that call, the control that actually matters for a public endpoint isn’t auth, it’s rate limiting: so nobody can slam the bot, run up cost, or knock it over.

And it has to be watched. You need to know when it breaks (see: the token), when it starts refusing things it shouldn’t, or when a source has drifted and a page needs re-flagging.

So the real list of what an organization is buying looks like this:

  • source ingestion
  • fact projection
  • retrieval boundaries
  • tool contracts
  • evals
  • release gates
  • monitoring
  • human review
  • deployment surfaces
  • rollback plans

That is not a chatbot project.

That is AI infrastructure.

GroundTruth

GroundTruth is the reusable version of the pattern.

It’s intentionally small. The sample domain is a tiny public library, because the library isn’t the point. The point is the loop:

  1. capture evidence
  2. project hard facts into a database
  3. compile explanations into a wiki
  4. expose both through tools
  5. force the assistant to use the tools
  6. run evals that catch bad paths
  7. refresh the system through reviewable diffs

In my current mental model, this is what a lot of enterprise AI systems are quietly trying to become.

Not a giant prompt.

Not a pile of embeddings.

Not a chatbot bolted onto the website.

A maintained truth layer with an assistant on top.

The job shape

This is also why I think there’s an emerging role here that most companies haven’t named well yet.

It’s not exactly prompt engineering.

It’s not exactly data engineering.

It’s not exactly full-stack engineering.

It’s not exactly product management.

It’s somewhere in the middle.

Someone has to understand the messy domain well enough to know which facts are dangerous. Someone has to build the data projection. Someone has to decide what the model may explain and what it must look up. Someone has to write the tool contract. Someone has to build the evals. Someone has to ship the UI. Someone has to debug the weird platform issues at 8am. Someone has to keep the system correct after launch — in public, at scale.

That’s the missing layer in enterprise AI: the person who can turn an organization’s scattered knowledge into an operating AI system that ships and stays right after the facts change.

Why I’m writing this

I built River Guide because students shouldn’t have to excavate a college website to answer basic questions about their next step.

But the pattern isn’t specific to higher ed. It applies anywhere the source of truth is scattered and the cost of a wrong answer is high: healthcare, government, insurance, finance, legal services, internal support, customer operations, compliance-heavy products, enterprise software.

Most organizations already have the knowledge. They already have the policies, pages, spreadsheets, PDFs, portals, people, and workflows. What they don’t have yet is the layer that makes that knowledge usable by an AI system without letting the AI invent the institution as it goes.

That’s the part I know how to build — and I’ve now done it end to end, in production, for a real institution.
