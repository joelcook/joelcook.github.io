The morning our giving site became a casino

A phone call, a hijacked giving site, and an attacker who could still get in after the patch.

23 Jul, 2026 · updated 12 Sep, 2026

It was a normal workday until I got a call: the school’s foundation website had been hacked. I pulled it up and found a casino.

The Indian River State College Foundation’s giving site was now a gambling page. The main college site was fine. Even the WordPress login looked normal. Apparently the institution had gone into a new line of business without telling anyone.

I helped get the site back. The better question was why it wouldn’t stay fixed.

The way in was a WordPress core vulnerability. There’s an AI angle here, too: the researchers who discovered wp2shell reported using a frontier model to find the exploit chain. That’s how the flaw was found. We don’t know what tools this particular attacker used.

WordPress had released a security fix. The attacker got in before we installed it. By the time the casino showed up, the site was already patched. Didn’t help. The attacker had built other ways back in.

Several WordPress installs shared one hosting account. Production, staging, and development looked separate in a browser. Underneath, they shared filesystem permissions. We found webshells, counterfeit plugins, admin accounts that shouldn’t exist, an SSH key, an FTP account, and processes still running as the hosting user.

Plenty to clean up. We preserved the suspicious files, compared them against logs and known-good code, removed the implants we’d confirmed, rotated credentials, and restored WordPress from official files. The homepage came back. The checksums matched.

Then the site broke again.

The clean index.php had been renamed, and a fresh casino payload had shown up. The patch was still there. The accounts and keys we’d removed hadn’t come back. Something else could still write to the site.

That something was a full-access cPanel API token, created during the original compromise. No expiration. No IP restriction. Changing the hosting password hadn’t touched it.

At that point the attacker didn’t need the WordPress bug anymore. They had a working credential for the system that controlled the files. We revoked the token, confirmed the token inventory was empty, and restored the clean files again.

The lesson was right there in the order things happened. We changed a password and assumed it did more than it did. Listing the active tokens told us what the password change couldn’t.

Google Search Console added one more wrinkle. Verification files and tags can let someone prove ownership again after their account is removed. We cleared out the unauthorized ones, plus a stale tag left behind by a previous provider.

The tag was gone from WordPress. It was still on the public page.

Nginx had cached it. A fresh request came back clean while a normal request kept serving the old proof of ownership. We purged the cache and checked both, including requests with a Googlebot user agent.

I used Codex to help inventory files, compare evidence, and rerun checks. People still made the calls: which accounts belonged, which files were malicious, which changes were authorized. Every one of those calls had to be backed by evidence.

By the end we’d checked the donation route, login, file checksums, accounts, processes, and tokens. A malware scan covered more than 82,000 files. A clean scan was nice to see, but that surviving token had already taught us not to trust any single check.

We found no evidence of donor or payment data being exported in the material available to us. That doesn’t prove no data was accessed; the formal impact review stayed with the institution.

Everyone saw the casino. The actual job was everything after the page looked normal again.
