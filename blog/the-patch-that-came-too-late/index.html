Our giving site was hacked. A leftover API token kept the attacker in.

The patch and a new hosting password didn’t lock the attacker out. Revoking one full-access API token did.

What happened

The Indian River State College Foundation’s giving site turned into a casino page. The main college site was fine.

How they got in

  • A WordPress core vulnerability, wp2shell. The researchers who found it reported using a frontier AI model to find the exploit chain.
  • The fix was out. The attacker got in before we installed it, and built other ways back in.
  • Several WordPress sites shared one hosting account and its file permissions.

What we found

  • Web shells
  • Fake plugins
  • Admin accounts that shouldn’t exist
  • An SSH key and an FTP account
  • Processes running as the hosting user

How we closed it

  1. Saved the suspicious files, compared them with logs and known-good code, removed every confirmed implant, rotated credentials, and restored WordPress from official files.
  2. The site broke again. Something could still write to it.
  3. Found a full-access cPanel API token made during the attack. Changing the password hadn’t touched it. Revoked it, confirmed none were left, restored the files.
  4. Removed unauthorized Google Search Console verification files and tags, plus a stale one from a former provider.
  5. Purged the Nginx cache, which was still serving an old verification tag, and checked again, including as Googlebot.

Checked at the end

  • Donation route, login, file checksums, accounts, processes, and tokens.
  • A malware scan of more than 82,000 files came back clean.
  • No evidence of donor or payment data being exported in the material available to us. That isn’t proof nothing was accessed; the formal review stayed with the institution.
  • Codex helped inventory files and rerun checks. People made every call.

Do this today

If you run WordPress on shared hosting, list the API tokens on the account. A new password doesn’t revoke them.
