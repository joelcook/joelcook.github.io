The Patch That Came Too Late

A technical incident report on a WordPress RCE, account-level persistence, and the control-plane token that survived the first cleanup.

23 Jul, 2026 · updated 27 Jul, 2026

At 8:46 on Thursday morning I opened the Indian River State College Foundation website and found a casino.

It was not a browser redirect or an ad-network problem. The production origin returned a 416 KB Indonesian gambling page with HTTP 200. wp-login.php still looked normal. The main college site was healthy. Only the giving site appeared broken.

The visible symptom suggested a replaced homepage. The evidence described a much larger system: WordPress had been exploited, the shared hosting account had been occupied, and new authentication paths had been created above WordPress. By the time the casino page appeared, the server was already patched.

Reconstructing entry

WordPress released 7.0.2 on July 17 for a critical vulnerability chain. The relevant advisories describe REST batch-route confusion leading to SQL injection followed by facilitated SQL injection in WP_Query. In sequence, the bugs enabled remote code execution. The request logs matched that public exploit path. 

Jul 17  WordPress 7.0.2 released
Jul 19  first malicious database artifact
Jul 21  site patched; hosting API token created
Jul 23  public defacement detected
Jul 25  attacker writes new artifacts
Jul 27  second failure exposes surviving token

The order matters. The attacker entered before the update. Patching removed the vulnerable code path, but a patch does not enumerate files, kill processes, delete accounts, revoke keys, or invalidate tokens created after exploitation. Exploit prevention and attacker eviction are different jobs.

Finding the real boundary

The domain was the wrong security boundary. Production, staging, development, and legacy WordPress installations lived under one Unix/cPanel account. To a browser they were separate sites. To a process running as the hosting user they were one filesystem.

We inventoried every document root and every mechanism that could write into one: Unix processes, SSH keys, FTP accounts, cron jobs, WordPress users, application passwords, plugins, database rows, and recently modified PHP. That produced webshells, counterfeit plugins, a reverse-shell kit, attacker-created WordPress administrators, an unauthorized SSH key, an FTP account, and live processes under the shared user.

The initial commands were deliberately boring:

wp core verify-checksums
wp user list --fields=ID,user_login,user_email,roles
wp plugin list
find <account-root> -type f -mtime -14
find <account-root> -type f \( -name '*.php' -o -name '.htaccess' \)
sha256sum <suspicious-file>

File size and modification time find candidates; they do not establish guilt. One unusually large .htaccess looked like an implant and turned out to be mostly a security plugin's block list. We hashed suspicious files, preserved copies, and correlated them with request logs, process state, known-good packages, and database records before changing anything.

Containment is an ordering problem

Deleting the casino page first would have improved the screenshot and damaged the investigation. The response instead followed a fixed sequence:

preserve  hash and quarantine evidence
contain   block webroots and stop confirmed attacker processes
evict     remove shells, users, keys, jobs, plugins, and database persistence
rotate    replace passwords, salts, database, FTP, and mailbox credentials
restore   rebuild code from known-good sources
verify    test each layer independently

Suspicious files moved into a locked quarantine rather than disappearing. Only processes tied to the intrusion were terminated. Unauthorized WordPress users, SSH keys, and FTP accounts were removed. WordPress salts and account credentials were rotated. Core was restored from official code, plugin provenance was reviewed, and PHP execution was disabled in upload directories.

This order reduces two risks: destroying evidence before scope is known and restoring a clean site while an attacker still has a valid write path. The homepage came back, core verified against official checksums, and the obvious persistence was gone.

Then the site failed again.

The token that survived

On July 27 the site returned the same 403. The canonical index.php was missing from its expected location. A clean copy had been renamed to index_old.php; its SHA-256 matched the previously preserved WordPress front controller. In its place were a new 855,237-byte casino payload, crawler content, altered discovery files, and the same webshell family found during the first response. Access logs showed the new payload had been requested on July 25.

WordPress was patched. The WordPress administrators were clean. The unauthorized SSH key and FTP account were gone. The attacker still had a higher-level capability: a full-access cPanel API token created on July 21, during the original compromise.

The token had no expiration and no IP restriction. It was also the only token in the account. Rotating the cPanel password had no effect on it.

password rotation != token revocation
patching          != eviction
clean homepage    != clean account

This was the recurrence mechanism. A control-plane token could modify files without using the WordPress vulnerability, an SSH key, or an FTP password. We had rotated a secret. We had not revoked the capability minted with that secret.

The fix was to revoke the token through the cPanel token interface, query the inventory again, and require an empty result before restoring the site:

uapi Tokens list
uapi Tokens revoke name=<compromised-token>
uapi Tokens list

The new artifacts went into quarantine. The known-good front controller was restored only after its hash matched the preserved copy. The site returned normally, but a working homepage was still not enough to call the incident closed.

Ownership outside WordPress

Google Search Console exposed a second class of persistence. An unknown owner appeared during the first incident while verification files were being placed on the site. Removing a Search Console user is not sufficient if the corresponding HTML file, meta tag, or DNS TXT record remains public. The account can prove ownership again.

We searched the webroots and database for verification material and removed unauthorized files. One remaining HTML meta tag belonged to a previous service provider rather than the attacker, but it was stale ownership proof and had the same security consequence. Yoast stored it in wpseo.googleverify:

wp option get wpseo --format=json
wp option patch delete wpseo googleverify

The database was now clean. The public homepage was not.

A normal request still contained the old tag and returned x-proxy-cache: HIT. The same URL with a cache-busting query was clean and returned a miss. WordPress had stopped emitting the proof; InMotion's Nginx cache was replaying an older page that still contained it.

curl -I https://giving.example.edu/
# x-proxy-cache: HIT

curl -I 'https://giving.example.edu/?verification-check=1'
# x-proxy-cache: MISS

The public purge route returned 403, while invoking the purge locally over SSH succeeded. After the purge, the first ordinary request was a clean miss and the next was a clean hit. We repeated the request with a Googlebot user agent. Both views were clean.

DNS verification was a separate control plane again. The zone was hosted in Azure DNS, not cPanel, so its TXT records required review by the Azure DNS administrator. “The website” was really WordPress, cPanel, Nginx, Search Console, and Azure DNS. Recovery had to follow ownership across all five.

Proving recovery

No single scanner could prove the account was clean, so we built a verification matrix. Each result answered one narrow question:

  • WordPress core 7.0.2 matched official checksums.
  • Fifteen of twenty plugins verified against public checksums; five commercial or custom plugins without public checksums were reviewed separately.
  • ClamAV scanned 15,704 directories, 82,728 files, and 8,033.56 MB in 26 minutes 54 seconds with zero detections.
  • The cPanel API-token inventory was empty.
  • Known malicious database markers, WordPress application passwords, unauthorized administrators, unexpected processes, and user cron entries were absent.
  • Only expected FTP users remained. The temporary response SSH key was revoked after the work.
  • The homepage, donation route, login, and active Yoast sitemap returned 200. Known malicious paths returned 404.
  • Normal browsers and Googlebot received the legitimate page, including a clean cached hit.

Zero antivirus detections is a useful signal, not a proof. A checksum proves a file matches a release; it says nothing about a token. A 404 proves a path is gone; it says nothing about a database administrator. Confidence came from independent checks agreeing across code, identity, process, database, network, and control-plane state.

There are still institutional follow-ups. cPanel two-factor authentication was disabled at the time of review. The hosting provider should terminate residual sessions and preserve its control-plane logs. Production and non-production sites should not share one account. DNS ownership and formal data-impact review belong with the teams that administer those systems.

Where Codex fit

Codex accelerated the mechanical work: enumerating the account, correlating files with logs, generating reversible commands, and repeating the same tests before and after each change. The human work remained scope, authorization, account legitimacy, evidence judgment, and approval of destructive actions.

The operating rule was simple: no important conclusion rested on an AI answer. It rested on an artifact, a command result, a hash, or a second independent test.

The actual fix

patch         closes the exploit
eviction      removes persistence
revocation    kills capabilities
verification  proves recovery

We found no evidence in the material available to us that donor or payment data had been exported. Shell access means absence of evidence is not proof of absence; formal impact assessment remains the institution's security and privacy responsibility.

The casino page was the loudest artifact, not the incident. The incident was an attacker retaining the ability to write files, create identities, and assert ownership after the vulnerable code had been replaced.

The page disappeared on the first day. Recovery took longer because recovery meant closing every known path back.
