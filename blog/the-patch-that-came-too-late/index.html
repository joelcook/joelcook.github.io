The morning our giving site became a casino

A phone call, a hijacked giving site, and an attacker who could still get in after the patch.

23 Jul, 2026 · updated 12 Sep, 2026

It was an ordinary workday until I got a call: the school’s foundation website had been hacked. I opened it and found a casino.

The Indian River State College Foundation’s giving site had become a gambling page. The main college site was fine. Even the WordPress login looked normal. The institution had acquired a new line of business without consulting anyone.

I helped get the site back. The interesting part was finding out why it wouldn’t stay fixed.

The entry point was a WordPress core vulnerability. There was an AI connection too: the researchers who discovered wp2shell reported using a frontier model to find the exploit chain. That explains how the flaw was discovered; we don’t know what tools this particular attacker used.

WordPress had released a security fix. The attacker got into our site before that update was installed. By the time the casino appeared, the site was patched, but the attacker had already created other ways back in.

Several WordPress installations shared the same hosting account. Production, staging, and development looked separate in a browser. Underneath, they shared filesystem permissions. We found webshells, counterfeit plugins, unauthorized administrators, an SSH key, an FTP account, and processes still running as the hosting user.

There was plenty to clean up. We preserved suspicious files, compared them with logs and known-good code, removed the confirmed implants, rotated credentials, and restored WordPress from official files. The homepage came back. The checksums matched.

Then the site broke again.

The clean index.php had been renamed, and a fresh casino payload had appeared. The patch hadn’t disappeared. The accounts and keys we had removed hadn’t returned. Something else could still write to the site.

That something was a full-access cPanel API token, created during the original compromise. It had no expiration or IP restriction. Changing the hosting password had left it valid.

The attacker no longer needed the WordPress vulnerability. They had a working credential to the system that controlled the files. We revoked the token, checked that the inventory was empty, and restored the clean files again.

The lesson was sitting right there in the sequence of events. We had changed a password and assumed too much about what that accomplished. An inventory of active tokens gave us the answer the password rotation couldn’t.

Google Search Console added another wrinkle. Verification files and tags could let someone prove ownership again after their account was removed. We cleared the unauthorized material and a stale tag belonging to a previous provider.

The tag was gone from WordPress. It was still on the public page.

Nginx had cached it. A fresh request looked clean while an ordinary request kept returning the old proof of ownership. We purged the cache and checked both responses, including requests using a Googlebot user agent.

I used Codex to help inventory files, compare evidence, and repeat checks. People still had to decide which accounts belonged, which files were malicious, and which changes were authorized. The evidence had to support each decision.

By the end, we had checked the donation route, login, file checksums, accounts, processes, and tokens. A malware scan covered more than 82,000 files. A clean scan was reassuring, but the surviving token had already shown why no single check was enough.

We found no evidence of donor or payment data being exported in the material available to us. That did not establish that no data had been accessed; formal impact review remained with the institution.

The casino was the part everyone could see. Following the evidence after the page looked normal was the work.
