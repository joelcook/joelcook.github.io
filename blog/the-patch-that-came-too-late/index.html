The Patch That Came Too Late

A WordPress patch closed the original hole. The attacker had already copied the keys.

23 Jul, 2026 · updated 27 Jul, 2026

At 8:46 on Thursday morning I opened the Indian River State College Foundation website and found a casino.

Not a clever redirect. A 416 KB Indonesian gambling page, served from the production origin with HTTP 200. WordPress login still looked normal. The main college website was fine. The separate giving site had been replaced.

By then the server was already running the patched version of WordPress.

This is the part worth understanding.

The patch worked

WordPress released 7.0.2 on July 17 for a critical vulnerability chain. The logs matched the public exploit path: REST batch-route confusion leading to SQL injection, followed by a facilitated SQL injection in WP_Query. Together, the chain led to remote code execution.

The first malicious database record appeared July 19. The site updated July 21. The public defacement appeared July 23.

The patch did its job. It closed the original door. It did not remove the people who had entered two days earlier, installed their own doors, and started making keys.

The domain was the wrong boundary

I opened Codex, gave it a temporary SSH key, and started read-only. Map every document root. Inventory users, processes, keys, FTP accounts, cron jobs, plugins, database rows, and recently modified PHP. Hash suspicious files before touching them.

The casino page was almost the least interesting artifact.

We found webshells, counterfeit plugins, a reverse-shell kit, attacker-created WordPress administrators, an unauthorized SSH key, an FTP account, and live processes under the hosting user. Production, staging, development, and old installations all shared that Unix account.

So I stopped treating this as a hacked homepage. Four websites can look separate in a browser and still be one machine to an attacker.

We blocked the webroots, terminated only confirmed attacker processes, and moved implants into a locked quarantine instead of deleting them. Then we removed unauthorized users and keys, rotated hosting, database, WordPress, FTP, and mailbox credentials, rebuilt from known-good code, verified official checksums, blocked PHP execution in uploads, and tested the origin and public site independently.

The scans were useful. The hashes were useful. The clean homepage was useful. None was a verdict by itself. Recovery came from agreement between different checks.

Then it came back

On July 27 the site failed again with the same 403. The real index.php had been renamed. A fresh casino payload and the same webshell family were back. The attacker had revisited the account on July 25.

The first cleanup had missed one capability: a full-access cPanel API token created during the original compromise. It had no expiration and no IP restriction. Changing the cPanel password did not revoke it. The attacker no longer needed WordPress, SSH, or FTP. They still had the hosting control plane.

That distinction is small in the interface and enormous in reality. We rotated the secret. We had not revoked the capability.

We revoked the token, confirmed the token inventory was empty, quarantined the new files, and restored the front controller from its known-good hash. A full scan covered 82,728 files with zero detections. Core matched 7.0.2. The known database markers, application passwords, attacker users, and active processes were gone.

Then another control plane surfaced: Google Search Console. During the first incident, an unknown account became an owner while verification files were being placed on the site. Removing a user from Search Console is not enough if their HTML file, meta tag, or DNS proof remains; they can simply prove ownership again.

We removed the malicious files, cleared a stale verification tag from Yoast, and purged InMotion's Nginx cache so Google could no longer see the old proof. DNS-hosted proofs required a separate review in Azure DNS. Website ownership had outlived the website compromise.

What the agent was good at

Codex did not magically know which contractor accounts were legitimate or when the institution should accept residual risk. Those remained human decisions.

It was very good at turning each observation into the next smallest test. Compare public DNS with the origin. Compare core with official checksums. Compare every credential inventory before and after revocation. Request the page as a browser and as Googlebot. Purge the cache, then prove both the cache miss and the next cache hit are clean.

It also got things wrong. A giant .htaccess file looked malicious at first and was mostly a security plugin's block list. The useful unit was never “the AI answer.” It was an operation with a rollback and an independent check.

Security response happens to fit this model well because so much of the work leaves evidence: a hash, a process, a row, a response code, a permission bit, a token inventory. Codex made the loop fast. The evidence kept the loop honest.

The fix

patch       stops the exploit
eviction    removes persistence
revocation  kills capabilities
verification proves the change

We found no evidence in the material available to us that donor or payment data had been exported. Shell access means absence of evidence is not proof of absence, so the formal data-impact decision still belongs with the institution's security and privacy teams.

The casino page was the loudest part of the incident and the least important. The incident ended only when the attacker could no longer write a file, authenticate to the account, mint another user, or prove to Google that the site belonged to them.

The page is gone. More importantly, the known attacker paths back are gone.
