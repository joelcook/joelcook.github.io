The Patch That Came Too Late

How a critical WordPress core vulnerability defaced a college Foundation website—and how I used Codex to contain the attacker, rebuild the site, and verify the recovery.

23 Jul, 2026

At about 8:46 on a Thursday morning, I opened the website for the Indian River State College Foundation and found a casino.

Not metaphorically. The homepage had been replaced by a large Indonesian gaming page. The WordPress login still looked normal, but the public site—the place where the Foundation tells its story and accepts donations—was gone.

The main college website was unaffected. This was the separate Foundation site at giving.irsc.edu. But the distinction did not make the morning feel less urgent.

I opened Codex and typed:

critical my website was hacked. its a wp site on inmotion hosting. where do i start?

I expected a checklist. What followed was closer to running an incident-response room with a very fast technical partner living inside my terminal.

By the end of the day, we had preserved the evidence, contained an active attacker, removed multiple persistence mechanisms, rotated the credentials, rebuilt production and staging, and verified the recovery through several independent tests.

The interesting part is not that an AI “fixed a website.” That framing is too magical and also wrong.

The interesting part is that security incident response turns out to be unusually compatible with an agent—if the human keeps control of scope, permissions, judgment, and the definition of done.

The homepage was not the incident

The first surprise was that not every observer saw the same page. One external check returned the legitimate Foundation homepage. A direct request to the hosting origin returned a 416 KB gaming page with HTTP 200. The login page was still real. Normal WordPress routes were broken.

That pattern matters. It suggested that the visible defacement might involve caching, conditional behavior, or code executing below the page layer. Simply opening WordPress Admin and changing the homepage would have been theater.

So we adopted a small incident-response loop:

preserve
contain
identify
evict
rotate
rebuild
verify

The ordering is the whole thing. If you delete first, you destroy evidence. If you patch first, you may close the original door while leaving the attacker inside. If you reopen before verification, you are testing your assumptions on real visitors.

I reset the hosting control-plane credentials, then gave Codex temporary SSH access using a dedicated public key. No password went into the conversation. The key could be revoked when the response was complete.

The first pass was intentionally read-only: map the domains, identify the document roots, inspect file metadata, compare WordPress core against official checksums, and preserve anything suspicious before changing it.

At first, a giant .htaccess file looked like the obvious culprit. It had been modified that morning and was roughly 27 KB. On inspection, most of it was a legitimate security plugin’s accumulated block list. Plausible hypothesis, wrong answer.

Then the actual artifacts started appearing.

The site was not the boundary

The production root contained webshells, counterfeit plugins, hidden plugin directories, a reverse-shell deployment kit, malicious verification files, and attacker-modified configuration. An unauthorized SSH key sat next to our temporary response key.

More importantly, there was a live attacker shell and a monitoring process already running under the hosting account.

This changed the unit of analysis. We were no longer cleaning a WordPress site. We were evicting an intruder from a shared Unix account.

The account also hosted staging, development, and legacy roots. The attacker had created a new FTP account, uploaded additional webshells, and planted two WordPress administrators in staging. Shell history showed account-level commands and an attempted privilege escalation.

So every webroot under that account became untrusted. We temporarily blocked them at the origin, killed only the confirmed attacker processes, removed only the unauthorized key, and preserved the relevant logs, databases, files, and command history.

This is a general security lesson disguised as a WordPress story:

Your blast radius is defined by the credential and execution boundary, not by the domain name in the browser.

Four websites that look separate to a visitor may be one security object if they share a hosting account, filesystem permissions, credentials, and process space.

The patch came too late

Once we correlated the HTTP logs, database rows, plugin artifacts, and timestamps, the entry path became clear.

On July 17, WordPress disclosed a critical vulnerability chain involving REST API batch-route confusion and SQL injection leading to remote code execution. The affected versions included WordPress 6.9.0 through 6.9.4 and 7.0.0 through 7.0.1. The patched releases were 6.9.5 and 7.0.2. WordPress considered the issue severe enough to enable forced automatic updates for affected sites. The release notice is unusually direct: update immediately.

Our first confirmed malicious record appeared on July 19. The attacker then installed several ways to return: plugins, webshells, an FTP account, an SSH key, and WordPress administrators.

The site updated to WordPress 7.0.2 on July 21.

The public defacement appeared on July 23.

So the site was patched when I found it. It was also thoroughly compromised.

This sounds paradoxical only if you think a patch is a cleanup tool. It is not.

A security update closes the door. It does not evict someone who already moved in.

The attacker no longer needed the original WordPress vulnerability. They had independent SSH, FTP, database, plugin, and webshell access. Updating core was necessary, but by itself it could never make the system trustworthy again.

The official advisories track the two linked issues as CVE-2026-63030 and CVE-2026-60137. The incident evidence included the same batch API paths, successful multi-status responses, and wp2shell markers associated with the public exploit chain.

What Codex was actually doing

It is tempting to summarize the day as “Codex removed the malware.” That misses most of the useful part.

Codex was continuously turning observations into the next smallest test:

  • compare the public hostname with the origin
  • distinguish a cached page from executable persistence
  • hash evidence before moving it
  • check official WordPress and plugin checksums
  • enumerate users, keys, processes, cron jobs, FTP accounts, and database records
  • scan for both known indicators and unfamiliar executable structure
  • make changes reversible by quarantining instead of deleting
  • test the recovered site from multiple paths before reopening it

In other words, the agent had sensors and actuators.

The sensors were SSH, HTTP responses, logs, hashes, filesystem metadata, WordPress CLI, database queries, checksum services, and antivirus scans.

The actuators were tightly scoped: block one webroot, terminate one confirmed process, quarantine a known artifact, rotate one credential, replace one configuration, run one fail-closed cutover.

I remained responsible for the policy layer. Which systems were in scope? When was evidence sufficient? Which accounts were legitimate? Which action was destructive? When could the public site reopen? Codex could accelerate the investigation, but it could not own those decisions.

This division of labor felt natural:

human
  intent, authorization, judgment, risk
        |
        v
Codex
  inspect, correlate, operate, verify
        |
        v
environment
  logs, files, processes, databases, HTTP

The conversation was not separate from the work. It became the control plane for the work.

The agent was wrong sometimes

This is important because a sanitized success story teaches the wrong lesson.

The large .htaccess file was initially treated as a primary indicator. It was mostly legitimate. Later, a configuration-hardening command damaged the final bootstrap lines of wp-config.php. The site was still blocked, a protected copy existed, and the mistake was repaired before traffic returned. The repair then had to pass PHP linting, a hash comparison, a WordPress bootstrap, and a live database query.

During staging recovery, an initial authenticated test appeared successful. A later sequence revealed that the hosting provider’s Nginx layer had cached an authenticated response and briefly served it without the outer password.

That was a real security failure in the first solution.

We disabled caching for the entire staging domain, purged the cache, and ran repeated unauthenticated/authenticated/unauthenticated cycles. Only after five consecutive 401 / 200 / 401 sequences—with the proxy explicitly reporting caching disabled—did we call the protection correct.

This is what people miss when they treat a capable model like an oracle. The model is not reliable because it sounds confident. The system becomes reliable when a wrong hypothesis or bad action is cheap to detect, reversible, and surrounded by independent checks.

Codex was useful partly because it generated and executed work quickly. It was safe enough to use because we made it prove the work.

Recovery is a proof, not a feeling

“The homepage looks right” is not a recovery criterion.

Before cleanup, we preserved a complete production filesystem image, database exports, logs, shell evidence, suspicious files, access inventories, and hashes. Confirmed malicious artifacts were moved outside the webroots and locked down, not erased.

We rotated the database credentials, WordPress salts, administrator passwords, application passwords, FTP accounts, hosting credentials, and the hosted mailbox. The temporary incident SSH key was revoked after the final verification.

Then we looked for agreement across different kinds of evidence:

  • WordPress core matched the official 7.0.2 checksums.
  • Every repository plugin in the trusted runtime matched WordPress.org.
  • Commercial components were compared, scanned, and reviewed by modification time.
  • Two antivirus passes scanned 76,167 files with zero detections.
  • Database searches found zero executable-content indicators.
  • Attacker users, FTP accounts, SSH keys, processes, cron entries, and known implant names were absent.
  • Known malicious URLs returned 403 or 404.
  • Uploads could not execute PHP.
  • The homepage, login, and internal pages returned the expected content through both the origin and public DNS.

No single check proves a system clean. Antivirus can miss custom payloads. Checksums do not cover custom plugins. A correct homepage says very little about an SSH key. The confidence came from the intersection of all the checks.

Only then did we reopen production.

Staging was a second incident

The contractor’s staging work was behind a temporary 403 wall, but it was not lost. The preserved database still contained 40 published pages, four drafts, and 281 media records.

We backed up the full 2.2 GB site and its database, verified WordPress and plugin integrity offline, removed the attacker-created administrators, upgraded staging to 7.0.2, normalized permissions, removed risky file-management components, blocked executable uploads, and placed the site behind a separate browser password.

The cache isolation bug made this take longer than expected. It also made the final result much stronger. The contractor got the work back in a clean, protected environment, and production remained untouched during the rebuild.

What changed afterward

The incident ended, but returning to the old operating model would have been a slow-motion repeat.

Production and staging now automatically install WordPress maintenance and security releases while major upgrades remain manual. File execution is blocked in uploads. Dangerous file-management and remote-control components remain removed. Non-production access is constrained. Credentials are separated and rotated.

The larger follow-up is architectural:

  • separate production and non-production into different hosting and credential boundaries
  • retire legacy installations instead of leaving them reachable
  • maintain off-host, immutable backups and practice restoring them
  • alert on new administrators, plugins, SSH keys, FTP accounts, and suspicious REST traffic
  • treat a shared hosting account as one security boundary
  • keep evidence and incident documentation outside the compromised system

There was no evidence in the material we could inspect that donor or payment data had been exported. That is not the same as proving no data was accessed. Because the attacker achieved account-level shell access, the formal data-impact decision belongs with the institution’s security and privacy teams.

The larger lesson

Security response is a good example of professional agentic work because much of it is verifiable.

A file has a hash. A process exists or does not. A core file matches the official release or it does not. A user is in the database or absent. A URL returns 200, 401, 403, or 404. A cache leaks authenticated content or survives a repeated isolation test.

The ambiguous parts remain human: deciding what matters, recognizing organizational consequences, knowing when an account name belongs to a contractor, determining whether residual risk is acceptable, and taking responsibility for reopening a public system.

Codex compressed a large amount of technical coordination into one day. It moved between networking, Linux, Apache, Nginx, PHP, WordPress, SQL, cPanel, logs, malware analysis, backup verification, and documentation without waiting for a different specialist at every boundary.

But the thing that neutralized the incident was not intelligence in the abstract. It was the loop:

observe
hypothesize
act narrowly
verify independently
record the evidence
repeat

The agent made that loop dramatically faster. The loop made the agent trustworthy enough to use.

The Foundation website is live again. The casino page is gone. The staging work survived. The attacker’s access did not.

And I no longer think of Codex as a tool that writes code.

In the right environment, with the right boundaries, it is a general technical operator. That is a much bigger idea—and a much more demanding responsibility.
