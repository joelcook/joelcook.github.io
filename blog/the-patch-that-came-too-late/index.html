The morning our giving site became a casino

A phone call, a giving site turned casino, and an attacker who could still walk right back in after the patch.

23 Jul, 2026 · updated 6 Oct, 2026

It was a perfectly ordinary workday until I got a call: the school’s foundation website had been hacked. I pulled it up and found a casino. An actual casino!

The Indian River State College Foundation’s giving site, the page that exists so people can donate to students, had been turned into a gambling page. The main college site was fine. Even the WordPress login looked normal. Apparently the institution had gotten into a whole new line of business without consulting anyone!

I helped get the site back. But the more interesting question, and the one worth writing about, was why it wouldn’t stay fixed.

The way in was a WordPress core vulnerability. And yes, there’s an AI angle: the researchers who discovered wp2shell reported using a frontier model to find the exploit chain. That’s how the flaw was found. We have no idea what tools this particular attacker used.

WordPress had released a security fix. The attacker just got in before we’d installed it. So by the time the casino showed up, the site was already patched. Didn’t matter one bit! The attacker had already built themselves other ways back in.

And they’d had plenty of room to work. Several WordPress installs shared a single hosting account. Production, staging, and development all looked nicely separate in a browser, but underneath, they shared filesystem permissions. So we found webshells, counterfeit plugins, admin accounts that had no business existing, an SSH key, an FTP account, and processes still running as the hosting user. Quite the haul.

We cleaned house. We preserved the suspicious files, compared them against logs and known-good code, removed every implant we’d confirmed, rotated credentials, and restored WordPress from official files. The homepage came back. The checksums matched. Victory!

Then the site broke again.

The clean index.php had been renamed, and a fresh casino payload had shown up. The patch was still in place. The accounts and keys we’d removed hadn’t come back. Something else could still write to the site.

That something was a full-access cPanel API token, minted during the original compromise. No expiration. No IP restriction. And changing the hosting password hadn’t touched it.

Think about what that means. The attacker didn’t need the WordPress bug anymore! They had a perfectly valid credential for the system that controlled the files. We revoked the token, confirmed the token inventory was empty, and restored the clean files once more.

Here’s the lesson, and it’s an embarrassingly simple one: we changed a password and assumed it did far more than it did. Changing the password felt like changing the locks. It wasn’t. Listing the active tokens is what actually told us who still had a key.

Google Search Console threw in one more wrinkle. Verification files and tags can let someone prove ownership again even after their account has been removed. So we cleared out the unauthorized ones, plus a stale tag a previous provider had left behind.

The tag was gone from WordPress. It was still on the public page!

Nginx had cached it. A fresh request came back clean while an ordinary request kept serving up the old proof of ownership. We purged the cache and checked both, including requests using a Googlebot user agent.

I had Codex helping inventory files, compare evidence, and rerun checks. But people still made every call that mattered: which accounts belonged, which files were malicious, which changes were authorized. And every one of those calls had to be backed by evidence.

By the end, we’d checked the donation route, the login, file checksums, accounts, processes, and tokens. A malware scan covered more than 82,000 files and came back clean. Nice to see! But that surviving token had already taught us not to trust any single check, no matter how green it looks.

We found no evidence of donor or payment data being exported in the material available to us. That’s not the same as proof that nothing was accessed, and the formal impact review stayed with the institution, where it belongs.

So if you run WordPress on shared hosting, go look at which API tokens exist on that account. Today. Everyone saw the casino. The real work was everything that happened after the page looked normal again.
