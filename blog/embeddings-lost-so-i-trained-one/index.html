Embeddings lost, so I trained one

A stock embedding model tied keyword search and was twice as slow. So I trained my own on one RTX 4090. It finds answers for half again as many real student questions, and RiverGuide answers with a third fewer model calls.

24 Oct, 2026

Three days ago I wrote that embeddings lost. A stock embedding model, Qwen’s 0.6B, found more abbreviations than keyword search, tied it on the test, and took twice as long doing it. So I kept BM25 and moved on.

Then America.gov put one line in its release notes: “We trained our own model in-house and streamlined how every question gets answered, so America.gov now responds 5x faster.” No details. No how. Fine! Here’s ours, with the how.

The problem was never the model that writes the answers. It was the catalog it searches. Students don’t type “Associate in Science in Radiography.” They type “rad tech.” Keyword search goes looking for the letters and comes back with nothing useful. The 27B Qwen that writes RiverGuide’s answers was quietly covering for it: rewrite the question, search again, read a page, search again. It got there. It just paid a model call every time it had to rephrase, and every model call is seconds of thinking.

So I took that same small model and taught it how students ask. The big Qwen wrote about 31,000 student-style questions about every chunk of the College’s site and catalog: the full question, the two-word search, the abbreviation, the misspelling. A small reranker threw out the questions their own page didn’t answer, and kept the tricky look-alike pages as wrong answers only when they really didn’t answer either. Then forty minutes of training on the same RTX 4090 that runs the answers. That’s it. That’s the whole in-house model.

Did it work? I didn’t want to grade it only on questions a model wrote. So I took the first question from every chat students had with the College’s assistant over the past month: 523 different questions, in their own words, typos and all. Only the counts left the box. For each question, the top five pages from each search were judged blind, shuffled and unlabeled. Keyword search found an answer for 59% of them. The stock model found one for 79%. Mine, 88%. Head to head, mine found 160 answers that keyword search missed. Keyword search found 11 that mine missed.

Now, inside RiverGuide the gap shrinks, because Qwen was already rescuing keyword search one rephrase at a time. But that rescue was the expensive part! So the Worker now runs the new model on the student’s own words before Qwen takes its first step, and hands over what it found. Most of the time, Qwen just answers. On RiverGuide’s 54-question test, run through the real Worker four questions at a time, tool calls fell from 111 to 75. A third fewer! The median answer came back 26% faster, and the average pass count went from 43.7 to 45.5. Same model, same prompt, same pages.

It wasn’t perfect the first time. The first version searched “What is my current GPA?” before Qwen could say what it should: we can’t see your records, here’s The River Portal. Two safety checks failed on every single run. A dozen lines now skip that first search when a student asks about their own records, and those checks pass again.

And the LLM wiki? Version one of RiverGuide still runs on one, and it’s good. Same 27B Qwen, same 54 questions, one at a time. The wiki got 49 answers right and the new setup got 50. The median was 5.2 seconds for both. But the wiki needed 2.37 model calls a question to the new setup’s 1.37, and 16,767 tokens to 8,921. Half the tokens, for the same answers! And one of the questions the wiki got wrong? Password resets. The College’s login page now lists a reset address, and the wiki has never heard of it. That’s the trouble with a second copy: somebody has to keep it true.

Now, some honesty. The judge on the real questions is a Qwen too, from the same family that wrote the training questions. And 54 is a small test, where a couple of questions swing from run to run. But 160 to 11 isn’t a rounding error.

It runs on the CPU, about 150 milliseconds a search, without touching the GPU. It went live on chat.riverboard.org on 24 October, with keyword search still standing behind it in case the box goes down. And it’s free: joeltcook/riverguide-retriever-full on Hugging Face, and the code that trained and tested it is on GitHub.

Your college has a website. Train yours on it. It’s an evening of GPU time.
